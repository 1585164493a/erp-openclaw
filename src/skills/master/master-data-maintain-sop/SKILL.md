# 主数据建档 SOP

> 本域管的是「**把数据建出来**」。与 `master-data-sop`（只回答"数据是什么"）配套使用：
> 那个是读，这个是写。**本技能的所有操作都会触发人工审批。**

## 1. 三个建档入口与必填字段

| 对象 | 工具 | 必填 | 可空（常见） |
|---|---|---|---|
| 供应商准入 | `supplier_create` | `name` | 编码（自动）、联系人、电话、邮箱、地址、信用评级、合作状态 |
| 客户开户 | `customer_create` | `name` | 编码（自动）、联系人、电话、邮箱、地址、客户类型、折扣等级 |
| 新商品建档 | `product_create` | `product_code`、`name`、`purchase_price` | 型号、规格、单位、建议零售价、安全库存阈值、供应商 ID、品类、描述 |

**枚举取值**（传**值**不传中文）：

| 字段 | 取值 |
|---|---|
| `supplier.credit_rating` | `A` 优秀 / `B` 良好 / `C` 一般 / `D` 较差 |
| `supplier.status` | `1` 合作中（默认）/ `0` 已停用 |
| `customer.customer_type` | `1` KA商超 / `2` 经销商 / `3` 电商 |
| `customer.discount_level` | `1` 一级（折扣最大）/ `2` 二级 / `3` 三级 |

## 2. 编码规则 —— 决定了「能不能自动生成」

| 对象 | 现有格式 | 能否自动生成 |
|---|---|---|
| 供应商 | `SUP001` … `SUP033` | ✅ 纯序号，无业务含义 → 不传则自动 `SUP+3位` |
| 客户 | `CUS00001` … `CUS00040` | ✅ 纯序号，无业务含义 → 不传则自动 `CUS+5位` |
| 商品 | `HFS-400-01`、`MG-90-01` | ❌ **带业务含义，必须由用户提供** |

### 商品编码 = 品牌缩写 - 规格 - 序号

**不要自己编造商品编码。** 若用户只给了商品名没给编码，按下面的品牌缩写表
**提出一个建议值请用户确认**，或直接问清楚。

| 缩写 | 品牌 | 品类 | 缩写 | 品牌 | 品类 |
|---|---|---|---|---|---|
| `HFS` | 澜溪 | 洗发护发 | `OM` | 洁力 | 洗衣护理 |
| `CLR` | 朗风 | 洗发护发 | `JF` | 柔洁 | 织物护理 |
| `LUX` | 雅致 | 沐浴清洁/洗发护发 | `WM` | 净威先生 | 家居清洁 |
| `DV` / `DVE` | 悦芙 | 洗发护发 / 沐浴清洁 | `WLX` | 雪悦 | 冰淇淋 |
| `VS` | 润舒 | 护肤护理 | `MG` | 梦享 | 冰淇淋 |
| `PD` | 净妍 | 护肤护理 | `CAND` | 甜心多 | 冰淇淋 |
| `ZH` | 中华 | 口腔护理 | `KL` / `KN` | 家悦 | 调味食品 |
| `JN` | 洁诺 | 口腔护理 | `LT` | 茶悦 | 茶饮冲调 |
| `LFB` | 卫宝 | 沐浴清洁 | | | |

**规格段**是容量数字（`400` = 400ml，`3000` = 3000ml/3L）；**序号段**为两位（`01`、`02`）
用于区分同规格的不同香型/型号。新增时先 `product_search` 看该规格已有哪些序号，取下一个。

**品类取值**（这 10 个是现有全集，尽量复用）：
冰淇淋 / 口腔护理 / 家居清洁 / 护肤护理 / 沐浴清洁 / 洗发护发 / 洗衣护理 / 织物护理 / 茶饮冲调 / 调味食品

**计量单位**：块 / 支 / 瓶 / 盒 / 组 / 罐 / 袋

## 3. 查重口径（建档前必做）

| 对象 | 查重工具 | 参数 |
|---|---|---|
| 供应商 | `supplier_query` | `name=...`（按名称模糊） |
| 客户 | `customer_search` | `name=...`（名称**或编码**模糊） |
| 商品 | `product_search` | `name=...`（按名称模糊） |

**为什么必须查**：数据库对三个编码列都有唯一索引，重复编码一定会被拒绝 ——
但那是在**人工审批之后**才报错，等于白白消耗用户一次审批。
查重不是"以防万一"，而是**避免让用户白点一次同意**。

查到同名或高度相似 → **停下来问用户**：「已有 XX（编码 xxx），是复用还是确实要新建？」

## 4. 引用完整性：`supplier_id` 必须真实存在

`product.supplier_id` 指向 `supplier.id`。**数据库里没有外键约束**，
所以填一个不存在的 ID 不会被数据库拦住 —— 但 API 会校验，填错直接报错。

因此：**用户给的是供应商名称时，先 `supplier_query` 查出 ID**。
- 查到了 → 用查到的 ID
- 查不到 → 说明该供应商**尚未建档**，提示用户"需要先做供应商准入"，
  **绝对不要编一个 ID 填进去**

## 5. 执行与审批（预期行为，不是故障）

三个写工具都挂了 `interrupt_on`，调用时系统会**暂停并要求人工 approve**：

- **approve** → 继续执行，拿到建档结果
- **reject** → 如实汇报"用户拒绝创建"，**不要重试、不要换工具绕过**

人工审批是这道域的设计目的（主数据建错会污染全链路），
不要在心理上把它当成障碍而想办法绕开。

## 6. 常见错误与应对

| 报错 | 含义 | 应对 |
|---|---|---|
| `编码已存在: XXX` | 重名 | 报告用户，询问改用其它编码还是复用已有档案 |
| `supplierId 不存在: N` | 供应商未建档 | 提示先做供应商准入，或让用户确认正确的供应商 |
| `参数校验失败: xxx (Field required)` | 必填缺失 | 按提示补齐；商品尤其确认 `productCode` 与 `purchasePrice` |
| `creditRating 只能是 A/B/C/D` | 枚举非法 | 把中文含义翻成取值再传 |
